TODO 캘린더 프로젝트 기초 구조 및 개발 방향
================================================

1. 프로젝트 개요
----------------

이 프로젝트는 기존 랜딩 페이지에서 별도 서비스로 이동하여 사용하는
개인 일정 관리용 TODO 웹 프로젝트이다.

서비스는 기존 랜딩 페이지와 분리하여 AWS EC2에서 독립적으로 실행한다.
현재 저장소에 구현되어 있는 React + Spring Boot 인증 구조를 기반으로 개발하며,
복잡한 협업 기능보다 사용자가 날짜별 할 일을 빠르게 등록하고 확인하는 데 집중한다.

핵심 목표:

- 월간 화면에서 날짜별 TODO를 한눈에 확인
- 주간 화면에서 일요일부터 토요일까지의 TODO를 비교
- 일간 화면에서 오늘 해야 할 일을 목록으로 확인하고 처리
- TODO 등록, 수정, 완료, 삭제 기능 제공
- PC와 모바일에서 모두 사용할 수 있는 반응형 화면 제공
- 기존 랜딩 페이지에서 해당 서비스로 자연스럽게 이동할 수 있도록 연결


2. 프로젝트 범위
----------------

1차 필수 범위(MVP):

- 기존 회원가입, 로그인, 로그아웃 기능 재사용 및 안정화
- TODO 등록, 조회, 수정, 완료 여부 변경, 삭제
- 월간 캘린더 화면
- 주간 TODO 화면
- 일간 TODO 화면
- 날짜 이동 및 오늘 날짜로 돌아가기
- 로그인한 사용자 본인의 TODO만 조회 및 변경
- 반응형 UI
- AWS EC2 배포
- 기존 랜딩 페이지에 서비스 이동 링크 또는 버튼 추가

추후 확장 가능 범위:

- TODO 중요도 및 카테고리
- 반복 일정
- 마감 시간과 알림
- 검색 및 필터
- 드래그 앤 드롭을 이용한 날짜 변경
- PWA 설치 및 오프라인 조회
- 통계 또는 완료 기록

초기 개발에서는 확장 기능을 먼저 구현하지 않는다.
월간, 주간, 일간 화면과 기본 TODO 기능이 정상적으로 연결되는 것을 우선한다.


3. 기존 프로젝트에서 활용할 부분
---------------------------------

현재 저장소는 다음 구성을 이미 가지고 있다.

- 백엔드: Java 21, Spring Boot 3, Spring Security, JPA, MySQL
- 인증: JWT Access Token, HttpOnly Refresh Token
- 회원 기능: 회원가입, 로그인, 로그아웃, 이메일 인증, 계정 복구
- 소셜 로그인: Google, Kakao 기본 구조
- 프런트엔드: React 18, TypeScript, Vite, React Router

기존 인증 기능은 최대한 유지하고 TODO 기능을 추가한다.
인증 코드를 처음부터 다시 만들거나 필요 이상으로 구조를 변경하지 않는다.

로그인한 사용자의 식별자는 백엔드 인증 정보에서 가져온다.
클라이언트가 전달한 userId를 그대로 신뢰하지 않으며,
모든 TODO 조회와 변경은 현재 로그인한 사용자의 데이터인지 서버에서 확인한다.


4. 서비스 구성 방향
-------------------

전체 흐름:

  기존 랜딩 페이지
        |
        | TODO 서비스 버튼 또는 링크
        v
  별도 AWS EC2 TODO 서비스
        |
        ├── React 프런트엔드
        ├── Spring Boot 백엔드
        └── MySQL 데이터베이스

권장 운영 방식:

- 기존 랜딩 페이지와 TODO 서비스는 서로 독립적으로 배포한다.
- 랜딩 페이지에는 TODO 서비스 주소로 이동하는 링크를 추가한다.
- TODO 서비스는 별도 서브도메인 사용을 권장한다.
  예: todo.example.com
- EC2에서는 Nginx가 정적 React 파일을 제공하고 /api 요청을 Spring Boot로 전달한다.
- 운영 환경은 HTTPS를 적용한다.
- DB는 팀의 운영 여건에 따라 EC2 내부 MySQL 또는 AWS RDS를 선택한다.
- 소규모 프로젝트에서는 EC2 한 대로 시작할 수 있지만 DB 백업 방안은 준비한다.

랜딩 페이지와 TODO 서비스의 로그인을 완전히 공유하는 작업은 별도의 인증 연동이 필요하다.
1차에서는 TODO 서비스에서 기존 인증 구조를 그대로 사용하고,
통합 로그인은 필수 범위에 포함하지 않는 것을 권장한다.


5. 주요 화면
------------

5-1. 월간 화면

- 일반적인 달력 형태로 한 달을 표시한다.
- 각 날짜 칸에 해당 날짜의 TODO 제목을 표시한다.
- 한 날짜에 TODO가 많으면 일부만 표시하고 "외 N개" 형태로 처리할 수 있다.
- 날짜를 선택하면 해당 날짜의 일간 화면 또는 TODO 목록을 연다.
- 이전 달, 다음 달, 오늘 이동 기능을 제공한다.
- 완료된 TODO는 체크 표시나 취소선 등으로 구분한다.

5-2. 주간 화면

- 일요일부터 토요일까지 총 7개의 날짜 칸을 표시한다.
- 각 칸에는 해당 날짜의 TODO 목록을 표시한다.
- 이전 주, 다음 주, 이번 주 이동 기능을 제공한다.
- 모바일에서는 7개 칸을 억지로 한 화면에 넣지 않고
  가로 스크롤 또는 날짜별 세로 카드 형태를 사용할 수 있다.

5-3. 일간 화면

- 기본 진입 날짜는 오늘이다.
- 선택한 날짜의 TODO를 목록으로 표시한다.
- TODO 추가, 완료 체크, 수정, 삭제를 가장 쉽게 수행할 수 있는 화면으로 구성한다.
- 이전 날짜, 다음 날짜, 오늘 이동 기능을 제공한다.
- 미완료 TODO를 먼저 보여주고 완료 TODO는 아래쪽에 구분하여 표시할 수 있다.

5-4. 공통 화면

- 로그인 및 회원가입
- 월간 / 주간 / 일간 보기 전환 메뉴
- TODO 등록 및 수정 폼
- 로그아웃
- 로딩, 데이터 없음, 오류 상태 안내


6. TODO 데이터 기준
-------------------

초기 TODO 데이터는 아래 정도로 단순하게 구성한다.

Todo:

- id: TODO 식별자
- userId: TODO 소유 사용자
- title: 제목
- description: 상세 내용, 선택
- todoDate: TODO가 표시될 날짜
- completed: 완료 여부
- completedAt: 완료 시각, 선택
- createdAt: 생성 시각
- updatedAt: 수정 시각

선택적으로 추가할 수 있는 항목:

- priority: LOW, NORMAL, HIGH
- startTime, endTime
- category 또는 color
- sortOrder

중요한 기준:

- 월간, 주간, 일간 화면은 서로 다른 데이터를 저장하는 기능이 아니다.
- 하나의 Todo 데이터를 날짜 범위에 따라 다르게 조회하여 보여준다.
- todoDate는 화면 표시 기준 날짜이므로 서버와 프런트의 시간대 기준을 통일한다.
- 초기 서비스의 기본 시간대는 Asia/Seoul로 설정한다.
- TODO 완료는 데이터를 삭제하지 않고 completed 값을 변경한다.
- 실제 삭제 기능은 사용자의 확인을 받은 후 처리한다.


7. 기본 API 방향
----------------

권장 API:

- GET    /api/v1/todos?from=YYYY-MM-DD&to=YYYY-MM-DD
- GET    /api/v1/todos/{todoId}
- POST   /api/v1/todos
- PATCH  /api/v1/todos/{todoId}
- PATCH  /api/v1/todos/{todoId}/complete
- DELETE /api/v1/todos/{todoId}

화면별 조회 예시:

- 월간: 달력에 표시되는 시작일과 종료일 범위 조회
- 주간: 해당 주 일요일부터 토요일까지 조회
- 일간: from과 to에 같은 날짜를 사용

API 원칙:

- 모든 API는 로그인 사용자를 기준으로 동작한다.
- 다른 사용자의 TODO는 조회, 수정, 삭제할 수 없다.
- Entity를 화면에 직접 반환하지 않고 Request/Response DTO를 사용한다.
- 제목은 필수이며 공백 제목은 허용하지 않는다.
- 날짜 형식과 입력 길이를 서버에서 검증한다.
- 잘못된 요청, 인증 실패, 권한 없음에 대해 공통 오류 형식을 사용한다.


8. 권장 디렉터리 방향
---------------------

현재 저장소 구조를 유지하면서 필요한 영역만 추가한다.

backend/src/main/java/com/teamproject/
├── auth/                 기존 인증 기능
└── todo/
    ├── domain/           Todo Entity, Repository
    ├── application/      등록, 조회, 수정, 완료, 삭제 처리
    └── presentation/     Controller, Request/Response DTO

frontend/src/
├── pages/
│   ├── MonthlyPage.tsx
│   ├── WeeklyPage.tsx
│   └── DailyPage.tsx
├── features/todo/
│   ├── api/
│   ├── components/
│   ├── hooks/
│   └── types/
├── components/           공통 버튼, 모달, 레이아웃
└── styles/               공통 스타일

실제 파일 이름은 팀원이 현재 코드 구조에 맞게 조정할 수 있다.
중요한 것은 화면, API 호출, TODO 처리 로직을 한 파일에 모두 작성하지 않는 것이다.


9. 권장 개발 순서
-----------------

1단계. 기존 프로젝트 실행 확인

- 백엔드와 프런트엔드가 로컬에서 실행되는지 확인한다.
- 회원가입, 로그인, 토큰 재발급, 로그아웃을 테스트한다.
- MySQL 연결과 환경변수 설정을 확인한다.
- 이 단계에서는 기존 인증 기능을 불필요하게 수정하지 않는다.

2단계. TODO 백엔드 기본 기능 구현

- Todo Entity와 Repository를 작성한다.
- 등록, 단건 조회, 날짜 범위 조회, 수정, 완료 변경, 삭제 기능을 구현한다.
- 모든 기능에 로그인 사용자 소유권 검사를 적용한다.
- API 테스트를 작성한다.

3단계. 공통 프런트엔드 구조 구현

- 로그인 후 진입하는 TODO 기본 레이아웃을 만든다.
- 월간, 주간, 일간 라우트를 구성한다.
- 보기 전환 메뉴와 공통 날짜 이동 UI를 만든다.
- TODO API 타입과 호출 함수를 구성한다.

4단계. 일간 화면 구현

- 오늘의 TODO 목록을 먼저 구현한다.
- 등록, 수정, 완료, 삭제를 연결한다.
- 일간 화면에서 기본 CRUD 흐름을 완성한다.

일간 화면을 먼저 완성하면 월간과 주간 화면에서도 같은 TODO 기능을 재사용하기 쉽다.

5단계. 주간 화면 구현

- 선택 날짜가 포함된 주의 일요일과 토요일을 계산한다.
- 7일 범위의 TODO를 한 번 조회한다.
- 조회 결과를 날짜별로 분류하여 각 칸에 표시한다.
- PC와 모바일 레이아웃을 각각 확인한다.

6단계. 월간 화면 구현

- 달력의 이전 달/다음 달/오늘 이동을 구현한다.
- 달력에 노출되는 전체 날짜 범위의 TODO를 조회한다.
- 날짜별 TODO 표시와 날짜 선택 동작을 구현한다.
- 한 날짜에 많은 TODO가 있을 때의 표시 방식을 정리한다.

7단계. 화면 간 연결 및 사용성 정리

- 월간에서 날짜 선택 시 해당 일간 화면으로 이동한다.
- 주간에서 TODO를 선택하면 수정 또는 상세 화면을 연다.
- 월간, 주간, 일간에서 수정한 결과가 서로 동일하게 반영되는지 확인한다.
- 로딩, 빈 목록, 네트워크 오류, 권한 오류를 표시한다.
- 모바일 화면을 점검한다.

8단계. 배포 준비

- 프런트엔드 운영 빌드와 백엔드 패키징을 확인한다.
- 운영용 DB, JWT Secret, 허용 Origin 등은 환경변수로 분리한다.
- Nginx에서 React 정적 파일과 Spring Boot API를 연결한다.
- HTTPS 인증서를 적용한다.
- EC2 재시작 후에도 서비스가 자동 실행되도록 구성한다.

9단계. 랜딩 페이지 연결

- 기존 랜딩 페이지에 TODO 서비스 소개 영역을 추가한다.
- "TODO 시작하기" 등의 버튼을 별도 EC2 서비스 주소에 연결한다.
- 새 창 또는 현재 창 이동 방식은 기존 랜딩 페이지 정책에 맞춘다.
- 배포 주소와 HTTPS 연결을 최종 확인한다.

10단계. 최종 테스트 및 인수인계

- 회원별 데이터가 분리되는지 확인한다.
- 월말, 연말, 윤년, 주 경계 날짜를 확인한다.
- 등록, 수정, 완료, 삭제 결과가 세 화면에 동일하게 반영되는지 확인한다.
- 새로고침과 직접 URL 접속이 정상인지 확인한다.
- 실행 방법, 환경변수, 배포 방법을 README에 기록한다.


10. 팀원 작업 분담 예시
-----------------------

백엔드 담당:

- Todo DB 구조와 API 구현
- 사용자 소유권 및 입력값 검증
- API 테스트

프런트엔드 담당 1:

- 공통 레이아웃과 일간 TODO CRUD
- API 연결 및 공통 TODO 컴포넌트

프런트엔드 담당 2:

- 주간 및 월간 화면
- 날짜 계산과 반응형 UI

배포 및 문서 담당:

- AWS EC2, Nginx, HTTPS, 환경변수 구성
- 랜딩 페이지 연결
- README, API 사용법, 테스트 결과 정리

작업 인원에 따라 역할을 합칠 수 있다.
백엔드 API 형식과 Todo 타입, 날짜 기준을 먼저 합의한 뒤 화면 작업을 병렬로 진행한다.


11. 구현 시 주의사항
--------------------

- 월간, 주간, 일간용 TODO 테이블을 각각 만들지 않는다.
- 브라우저가 전달한 userId만으로 데이터 소유자를 판단하지 않는다.
- 서버가 반환하는 날짜와 화면에서 사용하는 날짜 기준을 통일한다.
- 날짜 범위 조회 시 시작일과 종료일 포함 여부를 명확히 한다.
- 달력 라이브러리를 사용할 경우 라이선스와 React 버전 호환성을 확인한다.
- 달력 UI부터 과도하게 꾸미기보다 TODO CRUD 연결을 먼저 완성한다.
- AWS 비밀키, DB 비밀번호, JWT Secret을 Git에 올리지 않는다.
- 운영 환경에서 개발용 DB 비밀번호와 JWT Secret을 사용하지 않는다.
- EC2 보안 그룹은 필요한 포트만 허용하고 DB 포트를 외부 전체에 공개하지 않는다.


12. 완료 기준
-------------

다음 항목을 만족하면 1차 개발 완료로 본다.

- 사용자가 로그인하여 본인의 TODO만 관리할 수 있다.
- TODO 등록, 조회, 수정, 완료, 삭제가 정상 동작한다.
- 월간 화면에서 날짜별 TODO를 확인할 수 있다.
- 주간 화면에서 일요일부터 토요일까지 TODO를 확인할 수 있다.
- 일간 화면에서 오늘 또는 선택 날짜의 TODO를 관리할 수 있다.
- 세 화면에서 동일한 TODO 데이터가 일관되게 반영된다.
- PC와 모바일에서 주요 기능을 사용할 수 있다.
- 백엔드 테스트와 프런트엔드 빌드가 통과한다.
- AWS EC2에서 HTTPS로 서비스에 접속할 수 있다.
- 기존 랜딩 페이지의 링크를 통해 TODO 서비스로 이동할 수 있다.
- 실행 방법과 환경변수, 배포 절차가 문서화되어 있다.


13. 최종 개발 방향
------------------

이 프로젝트의 우선순위는 기능을 많이 추가하는 것이 아니라
"날짜별 TODO를 월간, 주간, 일간으로 편리하게 확인하고 처리하는 흐름"을 완성하는 것이다.

개발은 다음 순서를 기준으로 진행한다.

  기존 인증 확인
      -> TODO 백엔드 CRUD
      -> 일간 화면
      -> 주간 화면
      -> 월간 화면
      -> 반응형 및 오류 처리
      -> AWS EC2 배포
      -> 기존 랜딩 페이지 연결

1차 완성 후 실제 사용 결과를 확인하고,
필요할 때 중요도, 반복 일정, 알림, PWA 등의 기능을 순차적으로 확장한다.
